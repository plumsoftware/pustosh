# Шаг 2. Ассеты и данные

## Цель

Все спрайты из `assets/` попадают в игру через атласы Phaser в правильном размере и с правильной точкой привязки. Все `data/*.json` загружаются, проверяются и доступны из кода через типизированный `Registry`. В игре есть отладочная **галерея ассетов**, по которой видно, что всё на месте и в одном масштабе.

После этого шага любой следующий шаг создаёт спрайт одной строкой — `spawnSprite(scene, x, y, 'world.biome1_suburb.pine')` — и берёт числа только из `Registry`.

## Входные данные

- `assets/` (723 PNG), `assets_manifest.json`, `TZ/ASSETS.md` (масштаб, привязка, известные дефекты).
- `data/*.json` (12 файлов) и `data/README.md` (что в каком файле).
- Проект из шага 1 (Vite + Phaser + TypeScript, `src/core` без Phaser).

## Задачи

### 2.1. Исходники

1. Скопировать `assets/` и `assets_manifest.json` в `art/` в корне проекта — это **исходники**, в сборку они не попадают (`art/` не лежит в `public/`). Файлы в `art/` не редактировать.
2. Скопировать `data/*.json` в `public/data/`. Источник правды — эта папка; правки данных — отдельными коммитами с объяснением.

### 2.2. Упаковка атласов — `tools/pack-assets.ts` (`npm run pack-assets`)

Node-скрипт на TypeScript (запуск через `tsx`). Для ресайза — `sharp`; для упаковки — пакет с выводом в формат атласа Phaser (например `free-tex-packer-core`) или свой упаковщик MaxRects. Версии пакетов проверить и записать в `docs/VERSIONS.md`.

1. **Чтение манифеста.** Пропускать записи со `status: "replaced"` (их заменяют файлы из `replacements/`). Записи `status: "alternative"` упаковывать (используются как тир-1 инструменты и запасные иконки).
2. **Размер.** Целевой размер — из `scaleMode` и `targetPx`, **умноженный на 2** (атласы хранятся в 2x для чётких экранов телефонов; в игре спрайт рисуется в логическом размере):
   - `height` / `width` — пропорционально по высоте / ширине;
   - `fit_box` — вписать в квадрат;
   - `exact` (тайлы) — ровно 128×128;
   - `special` (стены, `building/walls`): лица (`face`, `window`, `window_boarded`, `door_opening`, `door`, `fence`, `damage_overlay`) — ширина 128, высота пропорционально (ожидается ~96; забор ~64); `top_cap` и `floor` — 128×128; `rubble` — по ширине 128;
   - `rig` (папки `characters/*`) — **без ресайза**, но не больше 512 px по длинной стороне: масштаб задаёт риг (шаг 4).
3. **Составные файлы** (`ASSETS.md §6`): из `animals/toad_tongue_and_sac` дополнительно сделать кадры `toad_tongue` (верхние 25% высоты) и `toad_sac` (остальное); исходный кадр `toad_tongue_and_sac` тоже оставить в индексе — на него ссылаются данные. Остальные дефекты не трогать.
4. **Группы атласов** — до 2048×2048, отступ 2 px, выдавливание края 1 px (тайлы — 2 px):

   | Группа | Папки | Загрузка |
   | --- | --- | --- |
   | `ui` | `ui` | при старте |
   | `icons` | `icons/*`, иконки из `replacements` (первые 11) | при старте |
   | `tiles` | `tiles` | при старте |
   | `walls` | `building/walls` | при старте |
   | `interior` | `world/interior`, `world/defense`, объекты мира из `replacements` | при старте |
   | `biome1` … `biome6` | `world/biome<N>_*` | biome1 — при старте, остальные — лениво |
   | `hero` | `characters/hero` | при старте |
   | `enemies`, `animals` | `characters/enemies`, `characters/animals` | при старте |
   | `bosses` | `characters/bosses` | лениво (у арены) |
   | `vehicles` | `vehicles` | лениво (у гаража/первой машины) |
   | `effects` | `effects` | при старте |

   Если группа не влезает в один лист 2048×2048 — многолистовой атлас (`multiatlas`).
5. **Выход** в `public/atlases/`: `<group>.png` (+ `<group>-1.png`… для многолистовых) и `<group>.json` в формате, который читает `this.load.atlas` / `this.load.multiatlas`.
6. **Индекс** `public/atlases/asset_index.json`:

   ```json
   { "world.biome1_suburb.pine": { "group": "biome1", "frame": "pine", "origin": [0.5, 1], "size": [124, 192] } }
   ```

   `assetId` = `<папка с точками вместо слешей>.<имя файла>` (как `id` в манифесте). `origin` из `pivot`: `bottom_center` → [0.5, 1], `center` → [0.5, 0.5], `top_left` → [0, 0], `rig` → [0.5, 0.5]. `size` — логический размер (1x) в пикселях.
7. **Кэш.** Хеш исходников и настроек в `public/atlases/.cache.json`: если ничего не менялось — скрипт завершается мгновенно.
8. **Отчёт** `docs/ASSET_REPORT.md`: размер каждого атласа (px и КБ), общий вес, **вес первой загрузки** (группы «при старте»), список пропущенных `replaced` и разрезанных файлов. Цель — первая загрузка до ~15 МБ; если больше — предложить WebP (флаг `--webp`, проверить поддержку в Safari) или понижение 2x → 1.5x для крупных групп.

### 2.3. Загрузка в Phaser — `src/game/assets/`

1. `PreloadScene` грузит `asset_index.json`, все группы «при старте» и все JSON данных; показывает полоску прогресса.
2. `AssetLoader.ensureGroup(scene, group): Promise<void>` — ленивая догрузка группы (биомы 2–6, боссы, транспорт) с маленьким индикатором в углу; повторный вызов не грузит второй раз.
3. Хелпер для всего остального кода:

   ```ts
   spawnSprite(scene, x, y, assetId, opts?): Phaser.GameObjects.Image
   // ставит текстуру group/frame, origin из индекса, масштаб = size / размер кадра (т.е. 0.5 для 2x),
   // depth = y (для объектов мира), бросает понятную ошибку, если assetId нет или группа не загружена
   ```

   Плюс `getAssetInfo(assetId)` и `iconFor(itemId)` (иконка предмета по `items.json`).
4. Проверка: в коде нигде нет строковых путей к PNG — только `assetId`.

### 2.4. Данные — `src/core/data/`

1. **Схемы zod** под каждый файл: `ItemDef`, `StationDef`, `RecipeDef`, `BuildingDef` (+ `MaterialDef`), `DefenseDef`, `EnemyDef`, `BossDef`, `BiomeDef` (+ `WorldObjectDef`, `HarvestDef`, `LootContainerDef`, `FurnitureSalvageDef`), `VehicleDef`, `SkillsDef`, `BalanceDef`, `RigsDef`. Обязательные поля — обязательны, неизвестные — допускаются (`.passthrough()`), чтобы данные можно было расширять. Типы — через `z.infer`.
2. Диапазоны дропа (`[min, max]`) — отдельный тип `Range`.
3. **Пути к картинкам** в данных (`assets/world/biome1_suburb/pine.png`) при загрузке превращаются в `assetId` (`world.biome1_suburb.pine`).
4. `loadGameData(raw: Record<string, unknown>): GameData` — парсит всё, собирает `Registry`, возвращает список ошибок. `core` не знает, откуда пришли JSON: в игре их даёт `PreloadScene`, в тестах — чтение файлов.
5. **`Registry`** — единая точка доступа: `items.get(id)`, `items.byCategory(cat)`, `recipes.byStation(id)`, `recipes.byOutput(id)`, `stations.get(id)`, `enemies.byBiome(n)`, `biomes.get(n)`, `objects.byBiome(n)`, `objects.get(biome, id)`, `building.material(id)`, `defense.get(id)`, `vehicles.get(id)`, `skills`, `balance`, `rigs`. Только чтение.

### 2.5. Валидатор — `tools/validate-data.ts` (`npm run validate-data`) + тест Vitest

Использует те же функции, что игра. Проверки:

- каждая ссылка на предмет (входы и выходы рецептов, дропы врагов и объектов, стоимости построек и защиты, топливо, патроны) существует в `items` / `stations` / `defense`;
- станок каждого рецепта существует; `requiresSkill` указывает на существующую ветку и уровень (`engineer_2` → ветка `engineer`, уровень ≤ 3);
- каждая картинка из данных есть в `asset_index.json` и не `replaced`;
- у каждого босса есть предмет-трофей; у каждого биома — босс, тайлы и хотя бы один враг; тайлы биомов существуют в `tiles`;
- каждый инструмент в `harvest.tool` — существующий `toolType` (или `hands`, `bucket`);
- нет рецепта, где результат нужен сам себе на том же станке;
- всё, что упоминается как `afterHarvest` / `stateSprites` / `closedSprite`, существует.

Вывод: список ошибок и предупреждений; код выхода ≠ 0 при ошибках. Тест Vitest: текущие данные — 0 ошибок; испорченная копия (несуществующий предмет в рецепте) — ошибка с понятным текстом.

### 2.6. Локализация

`public/i18n/ru.json` для строк интерфейса, функция `t('ui.play')` с подстановками (`t('hud.day', { n: 3 })`). Имена предметов, врагов, биомов — из `name_ru` в данных. Отсутствующий ключ в debug подсвечивается `[[ui.play]]`.

### 2.7. Галерея ассетов — `AssetGalleryScene` (F2)

1. Вкладки по группам атласов; спрайты в логическом размере сеткой, подпись `assetId`, точка привязки красным крестиком.
2. Фон: трава / тёмный / шахматка (чтобы видеть кайму и прозрачность).
3. Кнопка «Эталон» — рядом с выбранным спрайтом рисуется `characters.hero.ref_idle` в масштабе рига (96 px), чтобы сравнить размеры.
4. Вкладка «Тайлы» — каждый тайл повторён 4×4 (видно швы).
5. Вкладка «Стены» — комната 4×3 из каждого из 5 материалов, собранная по `building.json → assembly_rules` (упрощённо, без логики строительства).
6. Вкладка «Предметы» — все предметы из `items.json` иконками с названием и тиром (проверка, что у каждого предмета есть иконка).

## Критерии приёмки

- [ ] `npm run pack-assets` создаёт атласы, `asset_index.json` и `docs/ASSET_REPORT.md`; повторный запуск без изменений — мгновенный.
- [ ] В индексе нет ни одного `replaced`; у жабы есть кадры `toad_tongue`, `toad_sac` и исходный `toad_tongue_and_sac`.
- [ ] `spawnSprite` ставит любой объект с правильной точкой привязки: дерево и ящик стоят «на земле», иконки по центру.
- [ ] В галерее на тёмном фоне нет розовой и синей каймы (кроме случаев из `ASSETS.md §6`), тайлы повторяются без швов, комнаты из стен собираются без щелей.
- [ ] С эталоном героя: дерево ≈ 2 роста героя, машина в 1.5–2 раза шире героя, ящик ниже пояса. Найденные несоответствия исправлены в `targetPx` манифеста (`art/assets_manifest.json`) с записью в `CHANGELOG.md`.
- [ ] `npm run validate-data` — 0 ошибок; тест с испорченными данными падает с понятным сообщением.
- [ ] Биом 2 догружается лениво при вызове `ensureGroup('biome2')`, без зависания игры.
- [ ] Вес первой загрузки записан в отчёте и не больше ~15 МБ (или есть предложение, как уменьшить).
